# Benchmark Evaluation Protocol

## Why the synthetic 100% result is not the headline result

The original Tarang demo trains and evaluates on a generated traffic distribution. That is useful for a smoke test, but it is not strong evidence of generalization. The benchmark workflow therefore keeps the synthetic generator for development only and moves the headline evaluation to NSL-KDD.

The Canadian Institute for Cybersecurity describes NSL-KDD as a revised KDD'99 benchmark with non-redundant train records and a fixed train/test protocol; its current UNB page notes that the original distribution page is no longer available, so Tarang uses a pinned public mirror for reproducibility.

## Evaluation protocol

1. Download KDDTrain+.txt and KDDTest+.txt.
2. Verify the files against the pinned MD5 values recorded in scripts/download_nsl_kdd.py.
3. Use the training file to create an internal stratified validation split.
4. Fit the Random Forest on the training portion.
5. Fit Isolation Forest only on benign training rows.
6. Tune the Isolation Forest, Random Forest and hybrid thresholds on the validation split.
7. Keep KDDTest+.txt completely untouched until final evaluation.
8. Report accuracy, precision, recall, F1, balanced accuracy, ROC-AUC, average precision and a 2x2 confusion matrix.
9. Export per-record predictions and the exact protocol/threshold metadata.

## Run

    python scripts/download_nsl_kdd.py
    python scripts/benchmark_nsl_kdd.py

Or select output directories:

    python scripts/download_nsl_kdd.py --output-dir data/nsl-kdd
    python scripts/benchmark_nsl_kdd.py --data-dir data/nsl-kdd --output-dir artifacts/nsl-kdd

## Output

    artifacts/nsl-kdd/
    ├── benchmark_protocol.json
    ├── features.csv
    ├── hybrid_nsl_kdd.joblib
    ├── metrics.json
    └── test_predictions.csv

metrics.json is the source of truth for the benchmark table. The repository intentionally does not hard-code benchmark numbers.

## Why the benchmark adapter uses native NSL-KDD features

Tarang's original demo schema contains a compact 9-field flow record plus custom derived features. NSL-KDD has a different 41-feature schema. Forcing the benchmark through arbitrary lossy field mapping would create a misleading experiment. The benchmark branch therefore preserves the same hybrid architecture while using a benchmark-native preprocessing pipeline:

- numeric imputation + standardization
- one-hot encoding for protocol_type, service, and flag
- benign-only Isolation Forest fitting
- supervised Random Forest fitting
- validation-only threshold tuning
- untouched final test evaluation

This is the defensible comparison to describe in an interview.

## Suggested interview statement

> My first prototype used synthetic traffic for pipeline validation and reached 100%, but I did not treat that as production evidence because the data distribution was generated by the same logic as the detector features. I moved the headline experiment to NSL-KDD, kept the Isolation Forest unsupervised by training it only on benign training flows, tuned thresholds on a validation split, and evaluated once on the untouched benchmark test set. I report precision, recall, F1 and the confusion matrix alongside accuracy, so the result is not hiding false-positive or false-negative behavior.

## Important limitations

NSL-KDD is a classic benchmark, not a modern representation of all enterprise network traffic. The result should therefore be presented as benchmark evidence, not a claim of production readiness. A second validation on CICIDS2017 or a private organization-specific flow sample is a sensible next step.
